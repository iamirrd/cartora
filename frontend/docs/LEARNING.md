# یادگیری فرانت با کارتورا

این راهنما را به ترتیب بخوان و هم‌زمان فایل معرفی‌شده را باز کن. فایل‌های `node_modules` کتابخانه‌ها هستند؛ کد خودت داخل `src` است.

## مرحلهٔ ۱: صفحه و مسیرها

از `src/main.jsx` شروع کن: React روی عنصر `root` سوار می‌شود. `App.jsx` Providerها، چیدمان و مسیرها را به هم وصل می‌کند. React Router با `Route` تعیین می‌کند هر URL کدام صفحه را نمایش بدهد؛ نقش آن شبیه `urls.py` است، اما در مرورگر اجرا می‌شود.

`Link` به جای بارگذاری کامل سند، مسیر داخل برنامه را عوض می‌کند. برای لینک بیرونی همچنان `a` مناسب است. `useParams` شناسهٔ `/products/:id` را می‌خواند؛ شبیه آرگومان `pk` در view جنگو. `useSearchParams` فیلترها و صفحهٔ کاتالوگ را در query string نگه می‌دارد؛ در نتیجه Back مرورگر انتخاب‌هایت را برمی‌گرداند.

تمرین: در `App.jsx` مسیر `/about` و یک صفحهٔ ساده اضافه کن؛ بعد با `Link` از هدر به آن برو.

## مرحلهٔ ۲: داده، کامپوننت و هوک

مسیر دریافت کاتالوگ این است:

```text
CatalogPage → useProducts → catalogApi → client → Django
```

صفحه فیلترها را می‌گیرد، هوک چرخهٔ بارگذاری را مدیریت می‌کند، سرویس مسیر API را می‌شناسد، کلاینت HTTP می‌فرستد و `ProductCard` نتیجه را با prop دریافت می‌کند. کارت از شبکه خبر ندارد؛ مسئول نمایش است.

`useResource` همین الگو را برای صفحه‌های دیگر مشترک می‌کند. `useEffect` درخواست را پس از render اجرا می‌کند و cleanup با `AbortController` درخواست قبلی را کنار می‌گذارد. متغیر `active` اجازه نمی‌دهد پاسخ قدیمی بعد از خروج از صفحه، state را عوض کند.

سه وضعیت جدا داریم: بارگذاری، موفقیت و خطا. `Resource` آن‌ها را نمایش می‌دهد. خالی بودن لیست یک پاسخ موفق است، نه خطای اتصال.

تمرین: Network را باز کن؛ دسته یا ترتیب را تغییر بده و query string درخواست را با `ProductFilter` مقایسه کن.

## مرحلهٔ ۳: جزئیات و انتخاب تنوع

`ProductPage` محصول را با شناسه می‌گیرد. کامپوننت `ProductDetail` انتخاب تنوع، تصویر و تعداد را به کمک `useState` نگه می‌دارد. انتخاب تصویر فقط رابط را تغییر می‌دهد؛ افزودن به سبد یک درخواست POST است.

قیمت خرید از تنوع انتخاب‌شده می‌آید. `discount_price ?? price` مهم است: قیمت تخفیفی صفر می‌تواند معتبر باشد؛ با `||` صفر اشتباهاً نادیده گرفته می‌شود. قیمت‌های Decimal جنگو در JSON ممکن است رشته باشند، پس برای محاسبه یا مقایسهٔ عددی از `Number` استفاده می‌کنیم.

موجودی عمومی در serializer محصول نیست؛ صفحه ادعای موجودی دقیق نمی‌کند و اعتبارسنجی نهایی را به سرور می‌سپارد.

تمرین: دو تنوع با قیمت متفاوت بساز و ببین انتخاب هرکدام چگونه قیمت و دادهٔ POST را عوض می‌کند.

## مرحلهٔ ۴: فرم و اعتبارسنجی

در `AuthPage` اطلاعات فرم با `FormData` خوانده می‌شود؛ فرم ساده نیاز ندارد برای هر فیلد state جدا بنویسیم. در `AddressFields` فرم controlled است: مقدار از state والد می‌آید و `onChange` مقدار جدید را به والد می‌دهد. این روش برای پرکردن فرم از یک نشانی ذخیره‌شده مناسب است.

HTML با `required`، `type` و `pattern` اشتباه‌های ساده را زود پیدا می‌کند. اعتبارسنجی اصلی همچنان در serializer انجام می‌شود. `client.js` خطاهای فیلدی سرور را تبدیل به متن قابل نمایش می‌کند؛ بعضی پیام‌های شناخته‌شده ترجمه شده‌اند و پیام ناشناخته حذف نمی‌شود.

`useAction` هنگام ارسال درخواست دکمه‌ها را غیرفعال و خطا یا نتیجه را نگه می‌دارد. `useRef` جلوی ارسال هم‌زمان دوباره، حتی قبل از render بعدی را می‌گیرد. خطای شبکهٔ POST خودکار تکرار نمی‌شود؛ شاید سرور عملیات را انجام داده اما پاسخ نرسیده باشد.

تمرین: موبایل را با ارقام فارسی وارد کن و در Network ببین `AddressFields` آن را به ارقام لاتین تبدیل کرده است.

## مرحلهٔ ۵: ورود و Context

`AuthContext` اطلاعات کاربر را بین هدر و صفحه‌ها مشترک می‌کند؛ لازم نیست آن را از همهٔ والدها با prop عبور بدهیم. `session.js` نشست را در حافظه و `sessionStorage` نگه می‌دارد. رمز عبور ذخیره نمی‌شود.

کلاینت با `Authorization: Bearer ...` درخواست می‌فرستد. در پاسخ ۴۰۱، اگر refresh token باشد یک درخواست تمدید می‌فرستد و همان درخواست اصلی را یک‌بار تکرار می‌کند. درخواست‌های هم‌زمان از یک Promise مشترک تمدید استفاده می‌کنند. قطع اینترنت نباید refresh token معتبر را پاک کند؛ رد شدن refresh توسط سرور، نشست را پاک می‌کند.

`RequireAuth` رفتار رابط را کنترل می‌کند؛ امنیت واقعی همچنان permissionهای بک‌اند است. صفحهٔ خصوصی کاربر را به ورود می‌فرستد و مسیر قبلی را در state مسیریاب نگه می‌دارد. بعد از ورود به همان صفحه برمی‌گردد. خروج، refresh token را در سرور blacklist می‌کند.

پاسخ ثبت‌نام بک‌اند را با `UserSerializer` یکسان کردیم تا شناسهٔ کاربر بلافاصله بعد از ثبت‌نام هم موجود باشد؛ این شناسه برای نمایش کنترل‌های ویرایش نظر خود کاربر لازم است.

تمرین: مهمان روی افزودن به سبد کلیک کن، وارد شو و ببین دوباره به همان محصول برگشته‌ای. سپس صفحه را refresh کن.

## مرحلهٔ ۶: سبد خرید

`CartContext` اقلام، تعداد و جمع سبد را بین صفحه و هدر مشترک می‌کند. متدهای CRUD در `cartApi.js` جدا هستند. افزایش و کاهش تعداد PATCH و حذف DELETE است. بعد از موفقیت، داده دوباره از سرور خوانده می‌شود تا مبلغ یا تعداد حدسی نمایش داده نشود.

هر تنوع فقط یک‌بار می‌تواند در سبد باشد؛ برای تعداد بیشتر، همان آیتم را تغییر می‌دهیم. API اقلام فقط شناسهٔ تنوع را برمی‌گرداند؛ `CartRow` اطلاعات نمایشی آن را جدا می‌خواند. اگر کالا دیگر عمومی نباشد، شناسه همچنان نمایش داده می‌شود و امکان حذف آیتم وجود دارد.

سرور لیست‌ها را ۱۲تایی برمی‌گرداند؛ `list` همهٔ صفحات مجموعه‌های شخصی را جمع می‌کند تا مثلاً قلم سیزدهم سبد گم نشود. کاتالوگ بزرگ این رفتار را ندارد و صفحه‌بندی‌اش برای کاربر قابل انتخاب است.

تمرین: تعداد را بیشتر از موجودی ببر؛ باید خطا بگیری و جمع سبد مقدار نامعتبر را نمایش ندهد.

## مرحلهٔ ۷: نشانی و سفارش

`AddressesPage` دفترچهٔ نشانی با ساخت، ویرایش، حذف و انتخاب پیش‌فرض است. `AddressFields` در checkout هم استفاده می‌شود؛ این یک نمونهٔ واقعی استفادهٔ مجدد از کامپوننت است.

`CheckoutPage` فقط نشانی، روش ارسال و کد تخفیف را می‌فرستد؛ مبلغ قابل پرداخت را تعیین نمی‌کند. بک‌اند قیمت روز تنوع را snapshot می‌کند، هزینهٔ ارسال و تخفیف را حساب می‌کند و سبد را در تراکنش خالی می‌کند. فرانت پس از موفقیت شناسهٔ سفارش را می‌گیرد و به جزئیات آن می‌رود.

ثبت سفارش و پرداخت جدا هستند. خطای درگاه نباید POST checkout را دوباره اجرا کند. مبلغ پیش از ثبت، برآورد است؛ مبلغ قابل پرداخت در صفحهٔ سفارش مستقیماً از سرور خوانده می‌شود.

تمرین: یک کد تخفیف معتبر و سپس یک کد منقضی استفاده کن؛ پاسخ سرور و مبلغ سفارش را مقایسه کن.

## مرحلهٔ ۸: پرداخت و پیگیری

`OrderPage` سفارش، اقلام همان سفارش و تراکنش‌ها را می‌خواند. شروع پرداخت، POST به `payment/request/` است. چون بک‌اند فعلاً درگاه mock دارد، صفحه دو دکمهٔ واضح برای موفقیت و لغو آزمایشی نشان می‌دهد. بازکردن خودکار callback درست نیست؛ GET آن وضعیت پرداخت و موجودی را تغییر می‌دهد.

بعد از هر نتیجه، وضعیت و تراکنش‌ها دوباره خوانده می‌شوند. پس از شکست می‌توان از همان سفارش تلاش مجدد کرد؛ پس از موفقیت دکمهٔ پرداخت نمایش داده نمی‌شود. درگاه واقعی به پیاده‌سازی جدا در بک‌اند و جریان هدایت و بازگشت نیاز دارد.

دو فیلتر `filterset_fields` به viewsetهای موجود اضافه شده‌اند: `?product=...` برای نظرات و `?order=...` برای اقلام سفارش. ابتدا permission و queryset خصوصی فعلی اعمال می‌شوند و سپس فیلتر؛ دسترسی به سفارش دیگران باز نمی‌شود.

تمرین: یک‌بار پرداخت را لغو و سپس موفق کن. سفارش باید همان شناسه را داشته باشد و دو نتیجه را در تراکنش‌ها ببینی.

## مرحلهٔ ۹: قابلیت‌های حساب

`WishlistPage` تنوع‌های ذخیره‌شده را نشان می‌دهد و از همان انتخاب تنوع به خرید می‌رسد. `Reviews` نظرات یک محصول را می‌خواند؛ صاحب نظر می‌تواند ویرایش یا حذف کند. ثبت و ویرایش نظر نیازمند تأیید مدیریت است.

`NotificationsPage` اعلان‌های داخل سایت را می‌خواند و همه را خوانده‌شده می‌کند. Push مرورگر تنظیمات Firebase جدا می‌خواهد و با اعلان داخل سایت فرق دارد. `AccountPage` اطلاعات ثبت‌شدهٔ کاربر را نشان می‌دهد؛ API ویرایش پروفایل در بک‌اند فعلی موجود نیست.

## مرحلهٔ ۱۰: استایل و تست

`styles.css` ظاهر اولیهٔ کاتالوگ و `storefront.css` اجزای بقیهٔ فروشگاه را نگه می‌دارند. CSS Grid چیدمان اصلی و Flexbox ردیف‌ها را می‌سازند؛ media queryها تعداد ستون‌ها را در موبایل کم می‌کنند. فونت از بستهٔ محلی بارگذاری می‌شود.

تست‌های `tests/client.test.js` منطق حساس HTTP را بررسی می‌کنند: refresh، درخواست‌های هم‌زمان، خطا، نشست و صفحه‌بندی. تست‌های `tests/browser/storefront.spec.js` با مرورگر واقعی و پاسخ‌های کنترل‌شدهٔ API، مسیر کاربر را اجرا می‌کنند. این دو جای آزمایش اتصال واقعی به سرور و دیتابیس را نمی‌گیرند.

تست `tests/backend_contract.py` هم viewها و مدل‌های واقعی جنگو را با دیتابیس موقت در حافظه اجرا می‌کند: یکسان بودن پاسخ ثبت‌نام و ورود، فیلتر و مالکیت داده‌ها، سبد تا سفارش، لغو پرداخت و تلاش مجدد موفق، و جلوگیری از کاهش دوبارهٔ موجودی. از ریشهٔ پروژه اجرا کن:

```powershell
.\.venv\Scripts\python.exe frontend/tests/backend_contract.py
```

این تست به دیتابیس PostgreSQL پروژه وصل نمی‌شود و دادهٔ شخصی را تغییر نمی‌دهد؛ رفتار هم‌زمانی و قفل‌های PostgreSQL را هم اثبات نمی‌کند.

## چک‌لیست تست با بک‌اند واقعی

۱. بک‌اند را روی پورت ۸۰۰۰ و فرانت را با `npm.cmd run dev` اجرا کن.

۲. در admin دسته، برند، محصول، تنوع و موجودی فعال بساز؛ قیمت تنوع را بیشتر از صفر بگذار تا شبیه‌ساز پرداخت آن را بپذیرد.

۳. ثبت‌نام کن، یک تنوع را ذخیره کن، به سبد اضافه کن و تعدادش را تغییر بده.

۴. نشانی بساز و در checkout از آن استفاده کن. روش ارسال فعال را در admin بساز یا گزینهٔ بدون روش مشخص را برای آزمایش انتخاب کن.

۵. سفارش ثبت کن؛ مبلغ و نشانی را ببین. پرداخت را لغو و سپس از همان سفارش دوباره موفق کن. موجودی admin را بررسی کن.

۶. صفحه را refresh کن و از سفارش‌ها وضعیت را ببین. نظر بساز و از admin آن را تأیید کن؛ در حالت مهمان هم باید دیده شود.

۷. از حساب خارج شو و با حساب دوم وارد شو؛ سبد، نشانی‌ها و سفارش‌های حساب اول نباید نمایش داده شوند.

۸. بک‌اند را قطع کن؛ خطای اتصال را ببین، دوباره اجرا کن و «تلاش دوباره» را بزن.
